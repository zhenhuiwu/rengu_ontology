# 外部镜像与物理表读取契约修复（2026-10-31）

## 已确认的根因

- `governed_mirrors()` 原先仅声明平台 `ontology_id` 和业务字段；公共身份解析却无条件读取 `source.c.id`。没有业务 `id` 的对象会缺列，具有业务 `id` 的对象会把业务主键误作平台物理行号。
- 业务字段本身叫 `ontology_id` 时，原声明还会产生重复列。多个属性映射同一源列也有相同问题。
- 事件授权、动作目标、动态记录范围、规则读取中有相同的物理 `id` / 平台 `ontology_id` 假设。问数采样、总数、对象读取还有固定平台列名及优先使用本地 `backing_column` 的假设。
- 手动同步只执行一个有界批次；只有 `trigger=scheduled` 会进入续批状态，因此可能出现 `succeeded` 而 `complete=false`。
- 原签名包括绑定、对象、属性的全部 `lock_version` 和凭据密文，导致显示名称、描述等普通保存以及密码轮换也令镜像失效。另一条受控读取路径还曾在签名不一致时继续提供旧 payload，和严格镜像读取的失效规则不一致。
- 调度到期比较及任务时间原使用可冻结的业务时钟，存在业务演示时间影响实际后台任务的风险。

## 修复后的公共契约

`GovernedTable` 新增两个带兼容默认值的字段：

| 字段 | 原有本地表默认 | 外部镜像 |
| --- | --- | --- |
| `row_identity` | `id` | 平台镜像行 ID 的内部列别名 |
| `scope_column` | `ontology_id` | 平台本体 ID 的内部列别名 |

镜像内部别名从 `__mirror_row_id` / `__mirror_ontology_id` 起选，与所有业务列按大小写不敏感规则避让。业务 `id`、`code`、`ontology_id` 及同名候选内部字段均保留原值。重复源列只声明一次；重复映射的类型不兼容时不提供受控表。

内部列不进入业务 `columns` / `projection`。`row_identity_column()` 是查物理行的统一入口；`identity_rows()` 使用公开业务主键建立业务身份到平台行的映射。默认仍拒绝歧义；`unique_only=false` 供需要自行区分缺失与歧义的授权调用方查询候选。

外部 `source_sql` 明确包含当前本体、对象、镜像签名三个条件。共享 SQL guard 使用 `scope_column` 注入本体条件；公开查询仍仅能使用已授权业务投影。镜像属性读取使用 `source_column`，本地表继续兼容 `backing_column`。

相关改动位于 `common/sql_guard.py`、`common/object_identity.py`、`data/external_mirror.py`；本次适配了 `dynamic/action_options.py`、`dynamic/row_scope.py`、`dynamic/rule_runtime.py`、`qa/chain.py`、`qa/explore_api.py`、`static/metric_trial.py`。事件与动作模块由同轮其他修改消费相同契约。角色范围编译可显式传入当前会话受控 registry，空 registry 不回退到全局表；问数实例与指标将已批准物理列提供给行权限编译，输出字段仍保留属性 API 名。

## 同步、取消和恢复

- 原 `POST /external-read-bindings/{code}/mirror` 仍接收 `maxRows` 和 `restart`。`maxRows` 是每批上限，范围 1–1000；并非整次同步总行数。
- API 提交队列记录后，通过现有 `BackgroundTasks` 启动受强引用的异步任务，HTTP 请求不承担完整扫描的生命周期。手动任务持有既有对象级会话锁，逐批使用独立事务；每批都重新核验用户身份、权限、绑定、实际源位置和所选结构。
- 每次只读取 `batch_size + 1` 行，最多写入 `batch_size` 行。多出的行仅用于判断是否还有下一页；只有最后一次探测确认扫描结束才设 `succeeded` / `complete=true`。恰好 100 行且批大小为 100 时直接完成；101 行则先提交 100 行，再续读剩余行。
- `processed` 是该次全扫描累计提交的行数；失败、取消后的断点续传保留它和游标。运行历史的 `readCount` / `writeCount` 是各次任务自身提交的数量，不计入探测行。
- 新增 `POST /external-read-bindings/{code}/mirror/cancel`，无请求体。取消在当前事务批次边界取得锁后生效，状态为 `cancelled`；它保留数据和游标。它不会中断已经发给源驱动的查询。
- 失败或取消后，以 `restart=false` 再次提交可恢复；`restart=true` 是用户明确选择的从头扫描，仍采用 upsert，不清空镜像、不修改原绑定。
- 工作者携带固定 `run_id`，旧任务不能接管取消之后新建的任务。服务重启沿用既有恢复检查，把不再持锁的活动任务标为失败并保留已提交批次；不会静默启动生产同步。
- 定时同步保留原来显式授权、计划启用和每批授权检查；没有自动启用任何源计划。
- 已授权且签名有效的镜像在排队、运行、失败和取消时仍可注册。读取只包含本地当前可见行和本轮已提交行，元信息明确为 `partial`；第一次扫描没有行时可以返回合法的空镜像，事件身份处理可区分未同步与无权限。已知 stale / `restartRequired` 仍拒绝注册。

## 完整扫描后的源删除对齐

新增增量迁移 `data_0048_mirror_scan_visibility`，前置为 `admin_0047_login_sessions`。它只增加 `ExternalMirrorRow.last_seen_scan` 和 `is_current`：既有行最初为当前可见，之后新插入行默认非当前；物理行不删除。本机收尾已在完整备份后应用0048并核对列/default/索引，物理镜像76行保留；部署机仍须独立迁移。

迁移还建立 `(ontology_id, object_code, binding_signature, last_seen_scan)` 索引。部署步骤见[独立迁移操作单](26-10-31-mirror-database-migration.md)，本机已执行记录见[操作记录](26-10-31-deployment-integration-operations.md)。应先停止相关任务并备份部署自己的数据库，核对实际版本，再升级到明确revision；不要在文档或命令历史粘贴报告中的连接凭据，也不要用开发机备份覆盖部署数据。

每次新扫描把首次运行 ID 保存在 `cursor.scanId`，失败、取消后的恢复沿用这个扫描 ID。各批 upsert 更新已见标记及 payload，不更改既有 `is_current`。只有最后一批完整成功的同一事务，才把相同本体、对象、源签名下的行设为 `is_current = (last_seen_scan == scanId)`，同时提交 `complete=true`。未见的旧行由此退出当前可查询镜像，物理记录仍保留。成功发布还显式使受控表缓存失效。

失败、取消及运行中的读取使用 `is_current OR last_seen_scan = scanId`，保留未扫描的上次当前行，并允许读取本轮已提交的新行；这类结果始终标为部分扫描，不把中断误当成源删除。相同源键的 payload 仍按原有 upsert 更新，这不是不可变历史版本库，也不是原子源事务快照。

迁移前已完成的旧镜像可以继续读，但 `deletionsAligned=false`，必须明确显示删除待核对；下一次完整新扫描成功后才成为 true。迁移前的部分扫描没有已见标记，无法证明其历史前缀，本次只能保留数据并要求显式从头扫描，避免在恢复时误判删除。

缺少新列时，状态返回 `migrationRequired=true` / `errorCode=MIRROR_UPGRADE_REQUIRED`，完整标志为 false；创建同步及直读返回明确 409，受控 registry 不会登记缺列 SQL。本机已应用不代表部署端已具备新列，部署端必须独立确认。

## 源变更和签名

新稳定签名仅覆盖源身份和实际语义/安全映射：数据源编号、类型、地址、端口、限定库/schema/表、连接身份、TLS 配置、对象实际源表、发布状态、所选列、所选属性类型/敏感性/可见性/变换、解析后的源主键。它不包括密码、密文、密码摘要、显示名称、说明、更新时间、`lock_version` 或未选择的属性。

密码轮换不使新签名失效；下一次源检查/同步仍使用当前凭据核验连接与只读权限。它不使源密码成为镜像读取的权威依据。

已有旧签名仅在能够按当前完整旧元数据精确重算匹配时兼容读取和续传，内部使用旧算法核验。旧签名本身不作为 API 指纹输出。无法追溯已变化的旧元数据时不能推断为可信新源，必须明确重新同步；已有镜像行继续保留。

此兼容不意味着所有历史镜像立即免疫描述/版本变化：仍使用旧签名时，随后普通描述保存也可能破坏旧算法精确匹配。建议对仍能验证的旧镜像，先明确做一次完整同步升级为稳定签名；该过程保留定义、绑定及物理镜像数据。getter 不静默写数据库；旧已失配的记录必须确认来源后显式重新同步。

在可验证旧签名升级到稳定签名的扫描中，游标会保留已证明属于同一来源的旧签名，部分视图仍能读到尚未扫描的旧当前行。失败后重复从头扫描继续保留这个证明；若当前稳定源身份/映射已变化则不能沿用它。完整发布时移除这个兼容入口，之后不会重新露出旧签名下已被排除的源删除行。

每批还对所选源列的名称、内省类型类别及单列主键建立结构指纹，放入现有游标 JSON，不增加迁移。续传中结构不一致时标记 `restartRequired` 并失败，要求重新确认对象映射与读取绑定。新发现但未勾选的源列不会自动加入同步。结构指纹按内省提供的类型类别判断，不代表对全部数据库 DDL、数值精度或字符长度的完整审计。

镜像签名失配或已知所选结构失效时，两条读取路径均拒绝将旧镜像作为当前绑定提供；数据保留，授权不扩大。不再以“旧 payload 恰好有这些列”为理由复用另一份源的结果。

## 状态 API 与操作时间

状态增加 `currentStored`、`updatedAt`、`dataUpdatedAt`、`dataCheckedAt`、`dataPublishedAt`、`lastFinishedAt`、`runId`、`batchSize`、`resumable`、`restartRequired`、`sourceFingerprint`、`structureFingerprint`、`deletionsAligned` 以及上述增量升级提示：

- `totalStored` 包含保留的历史物理行；`currentStored` 仅统计当前源签名中符合可见性条件的行。
- `updatedAt` 是任务状态更新时间；排队、取消和失败也会改变它。
- `dataUpdatedAt` 是最近一个非空成功批次写入前记录的实际 UTC 时间，`dataCheckedAt` 包括成功的空批检查；二者随游标在事务中提交，不能作为源系统业务更新时间。旧记录没有此字段时返回空；不会用状态时间冒充数据时间。
- `dataPublishedAt` 只在成功完整扫描发布可见性时记录，也涵盖源删除导致当前行减少的发布。对象读取、问数结果及指标聚合携带镜像来源与 `mirrorCompleteness` 元信息；未完整完成或旧数据尚未核对删除时标记 `partial`，不会宣称为完整实时数据。
- `sourceFingerprint` 来自新的非凭据稳定签名，`structureFingerprint` 来自所选结构；都不会返回源配置明文或旧凭据派生签名。
- 任务开始/结束、状态更新、调度到期、默认 Cron 起算以及 heartbeat 统一使用实际 UTC。业务时钟、业务数据时间及用户环境文件不变。

## 明确的边界

这是用户授权触发的有界分页全扫描与本地 upsert，不能称为实时 CDC 或源数据库事务快照。分页之间源可能继续变化；游标之前新插入的键、已扫描行的后续更新，需要下一次明确扫描才能覆盖。成功完整扫描会排除未见旧行，但保留其物理记录；扫描期间源并发变化仍可能需要下一次核对。不同签名的旧行保留但不会进入当前签名查询。

批次行数有上限；源驱动调用的实际时长仍受现有驱动/网络超时能力约束，线程内已发送的达梦查询不能由取消 API 强行中断。没有新增自动按需生产同步，也没有执行动作、事件、远程数据库连接、清表或解绑。
