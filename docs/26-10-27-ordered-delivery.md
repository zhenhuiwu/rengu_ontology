# 本地持久顺序投递与真实回执入口

2026-10-27。增量保留全部历史事件、订阅投递记录及种子数据；未新增表、字段或迁移，未修改 `auto_ontology`。

## 本地顺序保证

复用现有数据库方言的事务级咨询锁和 `event_delivery` 状态。生产入站、投递认领及实际执行共用由 `event_type_id + obj_kind + object_id` 唯一确定的对象域锁，跨 worker、跨进程一致。规则执行先取 `ontology.publish` 锁，再取对象域及投递/事件锁，公开规则入口也将发布锁放在事件锁前。

定义声明顺序保证时，部署路由须显式增加 `"ordering": "object"`；该字段也可为原本不保证顺序的定义主动开启本地顺序。对象身份采用认证入站的 `objectType` 绑定及 `objectId`，随后按真实对象行权限校验。没有显式通道、稳定对象身份或完整原始入站快照，保持 pending，不尝试发送。路由 JSON 继续由原有 SecretStr 配置承载，不新增 Settings 字段。

同一对象域内按 `(occurred_at, eventId)` 排序，同时间采用数据库 C 排序的唯一事件 ID 打破并列。前序事件尚未生成投递记录时也会阻塞，不会因为 `discover` 每轮最多处理 200 条而越过前序。当前有序事件认领前，所有更早事件的全部启用订阅必须已经 delivered 或明确 skipped；前序 pending、processing、failed、unknown 均阻塞。因此订阅改名、定义版本切换不会绕开旧订阅的未决结果；没有配置的旧订阅也会阻塞整条对象流。

认领先独立提交 processing 与 attempts，再启动实际执行。任何后序事件已经产生持久 attempts 时，新到的更早事件在准备投递阶段标记 `quarantined / ORDERING_LATE_EVENT_QUARANTINED`，保留事件与投递记录，次数不增加，不发送；隔离记录不继续阻塞正常后序。这里的保守边界是“已经认领”，包括尚不能证明业务已执行的情况。

这保证本地已接收事件的调用顺序及确认屏障，不能重排已经发送或已经认领的业务事件，也不保证尚未到达的事件会被提前等待。不提供跨事件类型的全局顺序，不把 HTTP 接收确认当成远端业务处理完成。复合业务身份必须由生产方提供能稳定定位真实授权对象的 `objectId`；不会从说明文字或载荷摘要猜测分区键。对更细粒度对象缺少稳定建模时，仍需补齐真实对象映射后才能启用。

## 显式通道与失败边界

有序 HTTP 示例只展示字段形状，不包含真实地址或凭据：

```json
{
  "event_code/订阅名称": {
    "ordering": "object",
    "url": "https://subscriber.invalid/events",
    "test_url": "https://sandbox.invalid/events",
    "idempotent": true,
    "user": "已授权用户编号"
  },
  "event_code/规则订阅": {
    "ordering": "object",
    "rule_code": "真实已发布规则编码",
    "user": "已授权用户编号"
  }
}
```

HTTP 生产默认关闭，测试 URL/测试凭据继续与生产隔离。HTTP 超时、进程退出及未确认结果保持 unknown，不自动重发，不允许后序越过。failed 同样需要核查；本轮没有新增重试、解锁、人工改状态或死信补投接口。

显式 `rule_code` 路由只接 `app.contracts.rules.dispatch_event_rule(session, user, rule_code=..., event_id=...)`，不从“收到后”说明文本推断动作。订阅须为规则类型，快照中已有 ruleId 时必须与部署路由一致。公开入口负责重新校验真实身份、对象权限、绑定发布快照、规则条件与持久去重；返回的真实 ruleId、ruleVersion、hitId、alertId 和状态保存为最小回执。事件全部订阅完成且有 `status=alert_created` 与真实 alertId 时，事件结果显示“已生成告警”；去重回执即使引用旧 alertId，也仅算成功处理，详情保留真实旧告警引用。规则不能执行时保留失败回执，不伪造成功。动作路由和规则路由同时配置时明确拒绝派发。

测试事件只允许显式独立 HTTP 测试通道，规则/动作路由不参与测试排队，不生成真实告警或动作；同一测试事件中被发现的业务订阅也保持未执行。旧 seed 和没有原始入站快照的历史事件仍不补投递，不根据历史 outcome 编造订阅回执。

## 用户操作入口

构建区 → 事件类型 → 近期事件 → 点击真实事件 ID → 详情抽屉 →「订阅投递」。页签没有数字；列表从 `GET /api/ontology/v1/events/{eventId}/deliveries?page=1&size=10` 读取，默认 10 条/页，实际返回 total/page/size。显示“待前序完成”“结果待确认”“迟到事件已隔离”等中文状态；展开“投递详情”可看实际尝试次数、原因代码、前序事件、HTTP 回执或真实告警/动作编号。“刷新投递状态”仅重读，不修改状态。

旧事件无逐订阅记录时显示“暂无投递记录”；权限不足显示真实接口错误。模拟触发的结果弹窗复用同一回执组件，仍只对本人测试记录开放。接口继续过滤返回字段，不返回路由、URL、token、原始载荷或原始响应体。

## 本轮核验

- 事件模块相关改动与保留的最小边界检查通过 Ruff；事件 Python 文件通过 AST 语法解析。
- 留存 `backend/tests/test_event_delivery_boundary.py` 中的前序阻塞、未发现前序、迟到隔离与稳定锁域检查，未运行。
- 遵从用户限制：未运行后台测试、pytest、集成测试、迁移测试、长回归；未向真实外部系统投递、未生成验收用真实告警/动作。前端实际操作和统一类型检查由协调者记录。

未增加全局排序、自动补投或远端业务完成保证；未知/失败前序会持续阻塞，需先核查真实结果。
