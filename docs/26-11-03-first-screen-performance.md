# 定义页面首屏性能记录（2026-11-03，11-04 补充实测）

其他页面的同类扩查、角色/规则目录重复查询及实际页签复验见 [11月4日首屏扩查](26-11-04-screen-load-audit.md)。

用户反馈重点是进入页面后的首屏加载，涉及业务知识、维度详情和工作流目录，并非翻页算法。本轮保留真实分页与权限边界，先消除公共初始化和确定的重复请求；不据此宣称所有页面或环境的性能问题已经解决。

## 已定位和修复

业务知识当前列表由后端 `StaticRepo.page` 执行总数统计和 SQL `LIMIT/OFFSET`，适用范围关联只批量读取当前页，没有用前端截取全部记录伪装分页。`Glossary.vue` 使用 `StaticGate paged`，不会为了首屏加载完整对象、关系或函数目录；完整适用候选在进入编辑或新建时才读取。

公共开销来自请求身份与本体上下文初始化：此前每次设置本体范围都会加载受控表、绑定、镜像和关系信息，纯定义 GET 也承担业务取数准备成本。现通过 `definition_only_request` 的明确路由白名单，对符合条件的人类会话定义 GET 调用 `set_ontology_scope(..., load_data_bindings=False)`，跳过该准备过程。

另一处公共开销来自治理层对共享 SQL 表达式节点的重复遍历：CTE/DAG 的同一节点被沿不同路径反复访问。现按节点身份去重，保留权限检查结果，避免把共享子图当成树重复展开。维度映射总数统计也由 3 条 SQL 合并为 2 条，空结果为 1 条；列表主体仍由后端执行分页，没有改成前端截取或省略正确总数。

前端另有一个确定的重复读取：业务知识详情的监听键无条件包含 `workflow.loading`。列表选中首条后，工作流请求完成可再次触发相同详情读取。现在普通已发布视图不依赖此加载状态；草稿视图和仅草稿条目仍保留依赖，草稿编号、变更单加载/错误/目标、所选条目及本体上下文变化仍能触发必要刷新。`check-knowledge-detail-requests.mjs` 已用真实 Vue 响应式与延迟模拟响应检查该边界。

## 当前机器的真实 UI 观测

以下是主会话通过正常 UI 操作，在本体 1 使用本机临时 ASGI profiler 记录的请求 SQL 数量及后端耗时。profiler 只记录计数和时长，不记录 SQL 内容、参数或凭据；这些不是跨环境压测或浏览器整页加载时长。

下面是首轮消除公共绑定初始化后的观测，后续重载结果单列，避免混淆不同测量阶段。

| 请求 | 修改前 | 首轮修改后 |
| --- | --- | --- |
| `/api/ontology/v1/knowledge?page=1&size=19` | 27 条 SQL / 320 ms | 12 条 SQL / 121 ms |
| `/api/ontology/v1/change-requests?workflow=true` | 26 条 SQL / 311 ms | 11 条 SQL / 115 ms |
| `/api/ontology/v1/knowledge/{id}` | 26 条 SQL / 51 ms | 11 条 SQL / 15 ms |
| 业务知识列表第 2 页 | 未记录同条件修改前值 | 12 条 SQL / 19 ms |

11 月 4 日凌晨，DAG 修复加载后重新通过正常 UI 进入页面，本体 1 的实际请求如下。字节数为 profiler 记录的响应体大小。

| 请求 | SQL 数量 | 后端耗时 | 响应体字节数 |
| --- | --- | --- | --- |
| `/api/ontology/v1/knowledge?page=1&size=19` | 12 | 103.64 ms | 19254 |
| `/api/ontology/v1/change-requests?workflow=true` | 11 | 51.48 ms | 7051 |
| `/api/ontology/v1/dimensions/time?full=true` | 13 | 140.43 ms | 6884 |
| `/api/ontology/v1/dimensions/time/mappings?conflict=false&page=1&size=10` | 12 | 180.31 ms | 1982 |

用户报告中的 `dimensions/side?full=true` 与这里的 `dimensions/time?full=true` 使用同一处理器，但本体 1 这轮实际测量的是 `time`，不能将其写成 `side` 已实测。

同一台机器上，维度映射旧请求总耗时 1276.02 ms（数据库 39.60 ms、`PolicySession.execute` 1260.70 ms），新请求为 180.31 ms（数据库 68.26 ms、`execute` 155.87 ms）。这些计时有包含关系，不能相加。数据库耗时未下降，而治理执行层耗时明显下降，与 DAG 重复遍历的定位一致。

独立的纯内存遍历检查也验证了这一点：已发布页表达式由 120642 次访问降为 603 个唯一节点，约 215 ms 降至 0.95 ms；草稿由 430194 次访问降为 936 个唯一节点，约 1111 ms 降至 1.82 ms。这些是遍历检查数据，不是页面加载时长。

用户最初观察到的约 5 秒耗时，在当前机器本轮测量中尚未复现。不能把上述数据描述成“5 秒降到 19 毫秒”，也不能将单请求耗时视为整个首屏渲染时间。

## 保留的安全边界

- 轻量路径仅适用于明确登记的 GET；带 `Authorization` 的请求不进入该路径。API Key 业务请求仍执行完整本体绑定和行级范围处理。
- 白名单同时审查了页面伴随请求中的 `me`、`my-access`、当前工作空间、当前发布版及发布版列表，避免这些元数据 GET 重复承担无关绑定初始化；没有将任意 GET 都视为轻量请求。
- 身份、本体存在性与成员关系、功能权限、工作空间范围和事务 RLS 仍然每次重新检查，没有缓存权限结果、取消鉴权或放宽元数据权限。
- 轻量定义请求的 `row_filters={}` 不授予业务行读取权限；未知对象范围按拒绝处理。对象查询、指标求值、知识解析、动作等业务入口不因本次修改获得轻量路径豁免。
- 未改变列表总数、后端分页、历史视图或草稿读取合同；迟到响应仍不能覆盖新本体数据。治理代理已独立审查轻量路径边界。

## 验证范围与剩余差异

本轮已完成上述定义页面的正常 UI 重载和指定请求观测，不能据此宣称全站性能已验证。生产环境的网络往返时延、数据库负载、定义数量和关联规模可能不同；最初约 5 秒的完整耗时仍需在原环境以相同观测口径确认。当前数据没有覆盖跨环境负载测试或浏览器完整首屏渲染耗时。

本轮使用源码核查、窄内存断言及正常 UI 配合临时计数/计时观测，未运行后台全量测试或 pytest。本文不包含私有日志路径、真实凭据或用户目录。
