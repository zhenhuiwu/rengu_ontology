# 事件订阅投递与测试通道

2026-10-27。保留既有数据；只处理新接收、非种子、带完整入站定义快照的事件。旧事件不回填、不补投递、不改历史状态。

## 支持范围

- 内部认证入站沿用事件 ID 冲突检查、持久业务去重、本体发布版本绑定；另保存接收当时的事件定义快照，后续投递不借用当前订阅定义。
- 每事件/订阅名称唯一的一条 `event_delivery`，保存过滤、真实尝试次数、状态和最小回执。未匹配及非启用订阅跳过，不能算成功投递。
- 显式 HTTP 路由：实际 POST，只将真实 2xx 接收确认记为 `delivered`；拒绝响应为 `failed`；网络超时/进程中断为 `unknown`，需要人工核查，不盲目重发。发送稳定 `Idempotency-Key`，接收端必须明确承诺幂等。接收确认表示订阅方已收到，不表示其业务逻辑已经完成。
- 显式动作路由：通过 `app.contracts.actions.stage_event_action` 暂存真实待确认动作。路由用户须有事件管理、动作中心管理与对象行权限；参数必须按 API 显式映射，不能由摘要或收到后说明猜测。回执为真实动作编号及状态，订阅接收成功不代表动作执行成功。执行前若当前发布版与入站绑定版不同，明确失败，避免用新动作定义执行旧事件。
- 每次处理最多 200 条；一分钟调度。先独立提交 `processing` 再执行，异常退出五分钟后转未知并保留记录。没有配置不消耗尝试次数，保持 pending，一分钟后再检查。

## 配置与启动

默认 `RENGU_EVENT_DELIVERY_HTTP_ENABLED=false`，不会发送 HTTP。`RENGU_EVENT_DELIVERY_ROUTES` 是受 `SecretStr` 保护的 JSON 字符串；键为 `事件类型编码/订阅方完整名称`。不把路由、地址、token、原始响应体或原始载荷写入返回结果/日志。

示意配置仅使用不存在的域名：

```json
{
  "event_code/订阅名称": {
    "url": "https://subscriber.invalid/events",
    "test_url": "https://sandbox.invalid/events",
    "idempotent": true,
    "user": "已授权用户编号",
    "token": "由部署环境安全提供",
    "test_token": "单独的测试凭证"
  },
  "event_code/动作订阅": {
    "action_type": "真实动作类型编码",
    "user": "已授权用户编号",
    "params": {"动作参数API": "事件载荷字段API"}
  }
}
```

生产路由只接受 HTTPS；开发/测试允许回环地址 HTTP，不接受 URL 内凭据、查询参数或控制字符，不跟随重定向，不读环境代理。测试路由必须单独声明 `test_url`，不能等于生产 URL；测试不继承生产 token，只读取 `test_token`。生产 HTTP 也会按配置用户重新读取实际角色与对象行权限，未知映射或无授权默认拒绝。配置只由部署者提供，事件载荷及前端不能指定投递 URL、执行身份或动作参数映射。

迁移为 `event_0014`，接 `integration_0013`，只新增可空快照列与投递表，不修复或重写旧记录。协调者已在确认库名为 `rengu_ontology` 后应用该必要增量；没有运行迁移测试。

后端目录下运行 `python -m app.modules.event.worker`。使用现有 Procrastinate schema，队列为 `event-delivery`，周期任务为 `event.deliver`。配置变更后重新启动该 worker。不与其他队列共用工作进程。

## 前端入口与未配置边界

构建区 → 事件类型 → 选择已发布类型 →「模拟触发」。沿用保存的载荷示例与过滤条件；有匹配的显式 HTTP 测试通道才保存 `is_test=true` 事件并排队，弹窗展示测试事件编号及「刷新投递状态」。无测试通道只返回真实校验结果，不创建事件、不显示已投递；不使用生产 URL、不暂存或执行业务动作、不生成告警、不写下游业务对象。测试事件不计入真实事件流和统计。

真实投递查询：`GET /api/ontology/v1/events/{eventId}/deliveries`。生产事件依当前用户功能/对象行权限读取，测试事件仅创建者可读。结果只有名称、状态、尝试次数、错误码以及 HTTP 状态/动作编号；没有配置及密钥。

当前内置规则生成告警、通知、Kafka 等说明文字没有对应执行适配器；没有显式路由时保留 `DELIVERY_ROUTE_NOT_CONFIGURED`。有同对象有序保证的定义在没有有序通道时保留 `ORDERING_CHANNEL_NOT_CONFIGURED`，不擅自降级为无序 HTTP。未知结果只保留人工核查状态，本轮不增加用户未要求的重试/人工改状态入口。旧的无快照事件不投递，即使当前定义看起来相同。
