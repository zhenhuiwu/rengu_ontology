# 在保留已有数据的前提下升级

本升级包包含生成时工作区的后端源码、迁移、前端源码及已构建页面。**升级目标是原有部署机的现有平台数据库；不要导入本机演示 SQL 覆盖它，也不要执行 seed、清库或重建。** 本包没有连接配置、密钥、数据库备份或上传文件。

本次图谱更新只调整页面布局和展示，不要求迁移或重建用户的本体数据。问数修复保留受控表、字段和行权限检查；修正大小写引用不代表允许查询未授权表。需要更新后端和迁移的其他功能，仍按下述步骤独立评估目标数据库版本。

页面增加了窄视口滚动和视口高度回退，不改变用户系统缩放、浏览器缩放或本地数据。本轮针对 Chrome 102 增加 `100vh` 等回退，并让本体列表在容器内滚动；目标旧电脑上尚未进行视觉实测。项目不支持 Internet Explorer，其他旧浏览器仍需按实际版本验证。

## 操作前

1. 确认目标机正在使用的平台数据库、服务和前端目录。暂停售后端写入及后台调度，保留原程序、目标机 `.env`、数据源加密密钥、数据库角色和用户上传文件的安全副本。不要更换 `RENGU_DS_SECRET_KEY`：已有数据源密码需要原密钥解密；如确实丢失原密钥，应在目标系统重新输入相关数据源密码，而不是覆盖数据库。
2. 用目标机自己的数据库连接信息，通过匹配其 PostgreSQL 服务端版本的 `pg_dump` 对**目标机现有平台库**做完整结构和数据备份；验证备份文件完整并妥善保管。`backend/scripts/export_database.ps1` 仅适用于它明确限制的本机 `rengu_ontology`、端口 5433；条件不符时请使用目标环境现有备份工具，不要修改其限制后盲目运行。数据库备份不包含 PostgreSQL 全局角色及其授权，请另行保留原角色和权限配置。
3. 用当前部署环境的 Alembic 查看实际版本，并由管理员核对当前库结构及迁移路径。包中 `integration_0042_http_endpoints` 至 `data_0045_mirror_runs` 的升级操作为增列、建表、策略和授权，不删除已有业务表；它们需要已有 `rengu_ontology_scoped` 角色和执行迁移所需权限。若当前版本早于 `integration_0041_probe_path`、版本不在迁移链中、对象已被手工改动或权限不足，先评估缺失的全部历史迁移并处理，不要盲目升级。不能从本机数据库版本推断目标机版本。

## 部署

将包解压到**新目录**，保留原目录以便回退代码。不要用包内内容覆盖目标机 `.env`、密钥、数据库、上传文件或其他运行数据。按目标机原部署方式安装包内 `backend/pyproject.toml` 与 `backend/uv.lock` 锁定的依赖，确认目标配置仍指向原平台数据库，且有原 `RENGU_DS_SECRET_KEY` 和指向同一平台库的受限 `RENGU_QA_READONLY_DATABASE_URL`。只有备份和版本审查通过后，从新后端目录执行项目现有的 `alembic upgrade head`，再启动 API；升级失败即停止并查看具体错误，不运行 downgrade、seed 或数据库清空。达梦源库只需读取，不改变其配置和业务数据。

Windows 环境可使用原有服务管理方式启动新目录；前端将 `frontend/dist` 部署到原有静态站点，并保持 `/api` 指向对应 API。Docker 环境使用新目录构建镜像，通过目标机安全的环境配置和持久卷接入原库及上传文件；不要将 `.env`、备份或密钥复制进镜像。现有 Dockerfile 的默认启动命令包含 `alembic upgrade head`，因此**不能在完成备份和迁移审查前直接启动默认命令**。旧代码回退前应确认其能否识别已升级的数据库版本；不要自动降级数据库。

## 升级后检查

打开原有本体，先确认对象、指标和既有数据仍在。勾选字段仅表示授权，须确认源表已经映射到对象并保存受控读取授权；达梦外部表还需在“数据同步”查看同步状态，必要时按用户明确选择执行同步。问数只读取当前本体已授权映射，不应直接开放任意源表。检查 API `/readyz`、对象读取和原有问数；如果提示“不允许查询表”，记录表名和所属本体，核查实际部署版本、对象映射及同步状态，不要关闭 SQL 检查。指标保存与试算是两件事：绑定不可用时定义可保存，试算会明确显示不可用。

本说明和升级包已在本机准备；**目标机的备份、数据库版本、迁移及业务结果尚未核验**。
