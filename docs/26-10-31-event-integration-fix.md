# 事件投递联调修复与保留数据升级

本文说明事件代码行为与人工操作步骤，不包含环境地址、密钥、凭据或报告中的真实业务标识。没有执行后台测试、事件工作进程、生产请求或投递处置；后续获授权的本机0048镜像增量与API重启结果另见[操作记录](26-10-31-deployment-integration-operations.md)。

## 原因与修复范围

`prepare()` 原先把所有 `Unavailable` / `AppError` 都保留为 `pending`，每分钟再次检查。`attempts` 只计实际发送/业务执行，因此权限不足、对象身份歧义和配置错误可以在 `attempts=0` 下无限等待。`RETRY_ERRORS` 实际用于人工处置的可修复原因清单，并不是自动重试策略；现在已有明确注释，两种策略分开。

| 条件 | 修复后的状态与处理 |
| --- | --- |
| `EVENT_OBJECT_FORBIDDEN`、`EVENT_OBJECT_AMBIGUOUS`、`NO_PERMISSION`、`UNAUTHORIZED` | 检查失败即 `failed`，不轮询。已有同码 `pending` 也先终止，修复权限后不会自动回放，需针对该条记录明确人工重试/补投。 |
| `EVENT_OBJECT_NOT_SYNCED` | 具有对象完整行授权的订阅身份在外部镜像中找不到目标对象；每分钟等待，最长自投递记录创建起 15 分钟；到期转 `failed`，同步完成后可人工重试。 |
| `ORDERING_PREDECESSOR_UNRESOLVED` | 同样最多等待 15 分钟；超时保留前序事件标识并转 `failed`。人工先处置前序，再决定重试或跳过本条。 |
| 路由/身份/签名等配置错误 | 直接 `failed`；先修复条件，再在既有处置入口人工重试。 |
| HTTP 暂时性故障 | 沿用原来同一幂等键和 `max_retries` 限制的有限自动重试。 |
| `unknown` 或工作进程中断 | 继续保留结果未知与原始回执，必须人工核查；不自动转为可再次执行。 |

15 分钟是预检等待的保守上限：允许短暂同步滞后和前序执行完成，同时让持续性故障明确终止。它不提高任何授权，也不改变 HTTP 重试次数。已超过期限的等待记录即使在下一次检查时条件已恢复，也先结束等待，防止恢复后静默回放。人工重试仍会重新检查原始事件、订阅快照、对象授权、顺序、接收通道绑定与已有业务结果。

投递创建、到期、执行开始/结束与中断恢复使用真实UTC，区别于可冻结的业务时间；显式演示时钟不会让15分钟等待或HTTP重试时间永久停滞。旧记录保留原始创建时间，到期仍先转失败并要求人工决策。详见[部署联调操作补充](26-10-31-deployment-integration-operations.md)。

## 对象标识、镜像与权限

事件授权现在使用与镜像/物理表相同的受控 `row_identity_column()` 与 `scope_column`，不再把业务 `id` 当作物理行号。对象身份通过 `identity_rows(unique_only=False)` 的原始去重候选解析：零个候选与多个候选分开判断，拥有完整对象行授权时，两个物理行指向同一身份报告 `EVENT_OBJECT_AMBIGUOUS`，不会误报未同步。

先限定工作空间，并始终要求身份在当前工作空间内唯一，再检查目标行权限。只有完整对象行授权（行过滤为 `None`）且来源为外部镜像时，零个候选才报告 `EVENT_OBJECT_NOT_SYNCED`。部分行级授权下，缺行、身份碰撞和不可见对象统一为 `EVENT_OBJECT_FORBIDDEN`；即使碰撞中只有一行可见，也不能把它误当作唯一身份而投递，不披露隐藏行或其他工作空间的存在性。

异常列表允许拥有该对象完整行授权的用户查看当前工作空间的外部对象异常，即使该行尚未同步；部分行级授权仍要求真实可见行。详情只补充原定义版本、本体版本及原订阅过滤条件，不返回额外载荷。人工跳过仅变更异常处置记录；重试/补投仍要求执行身份的真实对象行校验通过。

## 过滤条件与版本

空字符串和纯空白过滤条件统一表示 `全部`：新保存会规范化，旧事件快照无需修改也可按该语义执行。非空且不可执行的表达式仍会被拒绝，并报告 `FILTER_NOT_EXECUTABLE`。

事件与订阅始终采用入站时快照。修改当前订阅不会更新旧事件，也不会把旧事件按新过滤条件重新投递。投递详情显示实际事件定义版本、本体版本和入站订阅过滤条件，便于区分“当前配置已修复”与“旧快照仍无法执行”。历史 `FILTER_NOT_EXECUTABLE` 失败仅在原快照过滤为空/纯空白时开放人工重试，不会自动执行；其他非空无效表达式及结构不完整的旧快照仍不开放重试，应核查业务后明确跳过。确需新业务事件时由生产方按正常入站与幂等规则产生新事件。

## 保留数据升级与逐条处置

以下是可审阅的操作步骤，未代用户执行：

1. 升级时保持通用事件工作进程停用。先修复镜像身份/同步机制与投递代码，保留全部事件、投递记录和处置历史，不改写历史快照。
2. 在事件类型的“投递异常”页按 `pending` / `failed` / `unknown` 预览，逐条打开“核查与处置”。也可只读调用现有 `GET /event-types/{typeId}/delivery-exceptions`、`GET /event-deliveries/{deliveryId}`、`GET /events/{eventId}/deliveries`；只在浏览器既有登录上下文中使用，不复制认证数据。
3. 先核对实际快照版本、过滤条件、原原因、原始回执、已有动作/告警及前序事件。旧权限/歧义 `pending` 不会因本次修复自动执行；可以在现有入口明确补投，或等待它转换为 `failed` 后重试。原有路由绑定、已有持久结果与乐观锁检查继续生效。
4. 对已经确认未执行且条件已修复的单条记录，使用现有 `retry` / `supplement` 处置，填写真实理由与核查证据。操作只把该条重新排队；工作进程真正执行前仍须通过全部检查。不要使用批量重放、修改订阅快照、直接 SQL 清错或删除历史。
5. 对无需继续执行的单条记录选择 `skip`。对未知结果先查接收端/业务结果，确认已接收时选择 `received`；确认未接收后才考虑重试。迟到隔离事件仅允许跳过。
6. 如果仅接收上线后新数据，复用工作进程已具备的 `--ontology`、`--event-type`、`--subscriber`、`--after-id` 选择模式：先只读记录上线前事件主键高水位，再显式配置这一固定值；它不会扫描高水位前的历史事件。该模式要求目标事件恰好有一个指定订阅方，不能用于多订阅事件。不要为处置单条积压而启动通用 sweep；历史记录继续留在异常页等待明确决策。

代码只主动终止旧权限/歧义失败和到期预检等待，不会把所有正常新 `pending` 或已有有限网络重试冻结。恢复通用工作进程前仍必须核对其扫描范围；`pending` 中无错误的既有事件会遵循原有队列机制，部署步骤中的停用和固定高水位用于避免历史积压被意外扫描。

## 遗留契约补充（2026-10-31）

- 事件快照明确声明 `ordering: "object"`（或既有“同一目标对象有序”）时，无需在自动规则路由重复配置同一保证：`check_order()` 在已有对象事务锁、前序阻塞与迟到隔离机制下直接执行对象保序。显式路由配置了其他顺序、或定义要求其他未知维度时仍报 `ORDERING_CHANNEL_NOT_CONFIGURED`，不能静默降为无序。排序继续使用发生时间与事件编码；迟到事件不会插入已经执行的流。
- 上文旧 `pending` 终止策略进一步覆盖已记录的配置错误，防止旧配置修复后静默回放。仅 `EVENT_OBJECT_NOT_SYNCED`、`ORDERING_PREDECESSOR_UNRESOLVED` 保留有界等待，`HTTP_RETRY_SCHEDULED` 保留原有限网络重试；其他带旧错误的 `pending` 先转 `failed`，由现有人工处置入口重新校验后单条重试。
- 已声明的对象载荷可以按 `reading.value` 读取。事件过滤、规则执行与只读回放、去重字段、规则动作映射及显式事件动作参数映射共用同一声明路径读取。规则条件选项也返回这些路径；对象和数组定义继续保存在现有 `schema` 字段。未声明子字段、缺失值及非对象中间层明确拒绝，不用零或其他默认值代替。数组仍需独立的明确索引/聚合契约，本次不猜测第一条或任意元素。
- 父对象和整数组读取也按已声明结构递归投影，包括数组中的嵌套对象。历史载荷中额外的键不会通过父对象条件的命中说明、函数输入或动作映射带出；标量定义实际携带对象/数组时拒绝读取。原始事件证据不改写。当前定义契约不接受 `additionalProperties` 等开放映射声明，因此不会猜测任意配置对象中的可读键。规则动作映射选项同步提供声明的嵌套路径。
- 受限条件解释器与规则解析统一支持未加引号的小写 `true` / `false`。引号中的字符串保持字符串；字段路径中的同名属性保持属性名。

外部生产方若将原始 HTTP 对象错误映射为零，平台无法重建丢失的真实值。需在生产方声明真实字段路径及单位变换；平台只对接收到的已声明原值求值，不针对某个业务字段补数。

本次运行 `backend/scripts/check_event_nested_contract.py` 的纯本地契约检查通过，覆盖嵌套标量/布尔、缺失与未声明字段、对象保序前序阻塞/迟到隔离、未知顺序拒绝，以及旧配置/权限错误禁止静默回放；相应 Python 文件静态编译通过。检查无数据库、网络、事件工作进程或真实业务写入，未运行 pytest 或全量测试；生产联调仍需部署代码、真实身份授权、已发布定义和合法新事件。
