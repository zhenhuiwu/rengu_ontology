# 用户状态生命周期守卫

## 确认的问题

编辑接口原先直接写body.status，能绕过停用接口的待审批检查；将启用用户改为待激活同样会失去访问能力，也没有检查。停用接口缺少当前登录用户和最后可恢复管理员保护。

多本体接入后，平台admin Session不绑定本体，旧pending_approvals直接查询CR/动作表会受RLS过滤为空，导致列表假0、停用检查漏掉其他空间待办。本轮修复这些实际调用路径，没有推断或搬移审批归属。

## 当前接口路径

| 路径 | 状态处理 |
|---|---|
| create→_new | 新建用户，默认待激活；仍需真实users:manage与角色分配所需roles:manage，不修改已有用户 |
| import→_new | 只新建通过校验且账号未存在的待激活用户，不把导入当状态更新 |
| update | 状态不变可按既有权限修改普通资料；变为停用/待激活时复用共享状态守卫，不通过直接status赋值旁路 |
| enable | 显式恢复启用，不添加角色/本体成员；保留既有认证限制 |
| disable | 复用同一状态守卫；已停用的重复请求不重复写状态审计 |

启用用户改为任一非启用状态前，拒绝当前登录用户自停用/自降为待激活；按真实SysRoleMember和角色func的并集识别同时具有users:manage、roles:manage的启用管理员，不能通过本轮用户状态流移除最后一位。不是按显示角色名或演示管理员标志判断。

更新、启用、停用使用同一生命周期事务锁和目标用户行锁，避免本模块并发状态变更同时通过最后管理员检查。**该保护只覆盖UserService状态流，不是整个角色CRUD、主角色单独调整或并发新审批分配的全局保底。** 不自动修复已有权限配置，也不扩大普通资料编辑权限。

## 跨本体待办读取

平台查询先从共享工作空间目录取得本体ID，再为每个空间建立独立Session，使用现有set_ontology_scope。原请求Session不切换scope，所有领域查询仍经过事务降权角色和RLS。只返回用户累计计数，不将领域审批内容返回平台列表。

读Session使用独立NullPool engine，复用现有QA只读连接启动参数，在事务开始前设置default_transaction_read_only与statement_timeout；不在after_begin已执行SELECT后补SET TRANSACTION READ ONLY。这样不会在请求连接池全部被外层请求占用时，再依赖同池第二条连接造成互等。完成或失败后释放连接和engine。

任一本体、CR或动作来源查询失败都向上失败，不转成0；状态写入在守卫之后，因此加载失败拒绝操作。有真实待办时继续使用TRANSFER_REQUIRED/TRANSFER_UNAVAILABLE错误，不自动转交、修改审批人或清理记录。

成功状态变更调用现有insert_audit，与状态写入同事务提交，仅记录用户编号及前后状态；失败整体回滚。前端当前用户的非启用选项禁用，服务端仍独立强制检查；保存失败保留表单。真实停用确认不再承诺旧会话可继续只读，后续请求按既有身份解析拒绝。

## 验证边界

本轮不新增schema，不进行实际用户状态或权限写入，没有后台测试、pytest、HTTP合成、集成/迁移测试。只做必要静态语法/类型检查；scripts/check_user_status_boundaries.py保留纯mock的状态守卫检查，未执行。

未实际验证自停用拒绝、其他本体有待办时拒绝、最后管理员拒绝、来源失败、成功状态审计或并发状态变更。跨模块角色写入与审批分配的并发一致性也未实测，不能因本次UserService修复宣称已全局覆盖。无生产登录/激活邮件系统接入，不清历史，不转交审批。
